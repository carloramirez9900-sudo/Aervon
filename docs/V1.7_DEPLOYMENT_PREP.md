# AERVON v1.7 — Deployment preparation

This document prepares the project for Railway + MongoDB Atlas + Telegram + BNB Smart Chain. It does **not** deploy anything.

## Recommended Railway topology

Create two Railway services from the same repository:

1. `aervon-backend`
   - Root Directory: `/`
   - Config file: `/railway.backend.toml`
   - Public networking: enabled
   - Healthcheck: `/health`

2. `aervon-frontend`
   - Root Directory: `/frontend`
   - Config file: `/frontend/railway.toml`
   - Public networking: enabled

Railway supports separate root directories for monorepo services. The config-file path is repository-absolute, so configure the paths exactly as shown above.

## Deployment order

1. Create MongoDB Atlas cluster/database user/network access.
2. Create backend Railway service, add backend variables, and generate a public backend domain.
3. Create frontend Railway service and set `VITE_API_URL` to the backend public domain.
4. Generate the frontend public domain.
5. Return to backend variables and set `FRONTEND_ORIGINS` to the exact frontend public domain.
6. Configure Telegram webhook only after the backend domain is live.
7. Verify `/health`, registration/login, dashboard, and admin access.
8. Configure BSC RPC and wallets with deposits/withdrawals paused operationally until chain tests are complete.
9. Enable deposit monitoring only after setting a safe `BSC_DEPOSIT_START_BLOCK`.
10. Enable withdrawals only after a small-value end-to-end test on the intended wallet.

## Backend variables

Copy `.env.railway.backend.example` into Railway Variables manually. Never upload an `.env` containing real secrets to Git.

### Core variables required for the API

- `NODE_ENV=production`
- `FRONTEND_ORIGINS`
- `MONGODB_URI`
- `MONGODB_DB_NAME`
- `JWT_ACCESS_SECRET`
- `TELEGRAM_BOT_TOKEN`
- `TELEGRAM_BOT_USERNAME`
- `TELEGRAM_WEBHOOK_SECRET`

`PORT` is injected by Railway and the backend already listens on `process.env.PORT` and `0.0.0.0`.

### Generate application secrets

Run locally:

```bash
node scripts/generate-app-secrets.mjs
```

Copy the values into Railway. Do not commit the output.

## Frontend variables

Set in the frontend Railway service:

```env
VITE_API_URL=https://YOUR-BACKEND-DOMAIN
```

This variable is embedded at build time by Vite. If it changes, redeploy/rebuild the frontend.

## CORS

The backend must receive the exact public frontend origin, without a trailing path:

```env
FRONTEND_ORIGINS=https://YOUR-FRONTEND-DOMAIN
```

For multiple trusted frontends, separate values with commas.

## MongoDB Atlas

Recommended production setup:

- dedicated Atlas database user for AERVON;
- strong generated password;
- TLS connection string (`mongodb+srv://...`);
- database name `aervon`;
- do not reuse a personal/admin Atlas account credential in the application URI;
- restrict Atlas network access as tightly as your Railway/Atlas setup permits.

MongoDB transactions require a replica set; MongoDB Atlas provides this on normal clusters and is therefore appropriate for the ledger implementation.

## Telegram

After backend deployment, Telegram must send updates to:

```text
https://YOUR-BACKEND-DOMAIN/auth/telegram/webhook
```

The webhook must be registered using the same secret stored in `TELEGRAM_WEBHOOK_SECRET` via Telegram's `secret_token` option. The backend checks the `X-Telegram-Bot-Api-Secret-Token` header.

Do not put the bot token in the frontend.

## BNB Smart Chain

Current configured network assumptions:

- Chain ID: `56`
- Asset: USDT BEP-20
- configured token contract: `0x55d398326f99059fF775485246999027B3197955`

Before sending real funds, independently verify the token contract and RPC network in BscScan/provider tooling.

### RPC

Use a production BSC RPC provider endpoint as `BSC_RPC_URL`. Do not use a browser/public frontend key for the backend.

### Deposit addresses

The API can derive public deposit addresses from `BSC_DEPOSIT_XPUB`, which is preferable to exposing a seed to the address-generation path.

UPDATED in v1.9: The public API uses only the XPUB; a separate private signer receives the mnemonic and signs restricted Treasury-only sweeps. Read `V1.9_ISOLATED_DEPOSIT_SIGNER.md`. Meaningful production custody still warrants KMS/HSM/MPC and isolation of gas/withdrawal private keys.

### Withdrawal wallet

The current implementation supports `BSC_WITHDRAWAL_PRIVATE_KEY` as an environment secret. This is acceptable only as a controlled launch-stage configuration with limited hot-wallet exposure. For larger balances, migrate to an isolated signer/KMS/MPC.

The withdrawal engine has no fixed BNB floor. It checks that the wallet has enough BNB for the estimated transaction gas plus the configured margin (`BSC_WITHDRAWAL_GAS_MARGIN_BPS`).

## Safe launch order for blockchain functions

Do not enable all money movement at once.

1. Start API/frontend with operational deposit/withdrawal processing paused from Admin.
2. Confirm the configured withdrawal address and treasury address.
3. Verify BSC RPC reports chain ID `56`.
4. Verify USDT contract address.
5. Test one unique deposit address with a small amount.
6. Confirm deposit detection and ledger credit exactly once.
7. Test sweep with a small amount.
8. Test a small withdrawal to a controlled address.
9. Verify `txHash`, amount, gas, confirmations, ledger and audit record.
10. Only then enable normal operation.

## First SUPER_ADMIN

1. Register and Telegram-verify the intended administrator account normally.
2. Set:

```env
ADMIN_BOOTSTRAP_ENABLED=true
ADMIN_BOOTSTRAP_PHONE=+<verified-number>
```

3. Restart/deploy the backend once and confirm the role.
4. Immediately change:

```env
ADMIN_BOOTSTRAP_ENABLED=false
```

5. Redeploy/restart.

There is no public endpoint that turns an arbitrary user into the first administrator.

## Railway health check

Backend health endpoint:

```text
GET /health
```

It returns `2xx` only when MongoDB is connected. Railway should use `/health` as its deployment healthcheck path.

## Pre-production checks

Before allowing real users/funds:

```bash
# backend
npm install
npm run build
npm test
npm run lint

# frontend
cd frontend
npm install
npm run build
npm test
npm run lint
```

These commands must pass in an environment with dependencies installed. Previous ChatGPT build attempts were limited by dependency-install timeouts and therefore are not a substitute for this step.

## Security blockers before larger balances

The following are intentionally documented as launch-hardening work, not hidden:

1. Move refresh token handling from browser-accessible storage to HttpOnly/Secure cookie or BFF architecture.
2. v1.9 already isolates the deposit mnemonic in a PRIVATE Railway signing service. Before keeping significant funds online, additionally isolate the gas-wallet and withdrawal keys through KMS/HSM/MPC and complete a custody/security review.
3. Add external uptime/error monitoring and alerting; Railway deployment healthchecks are not continuous monitoring.
4. Back up operational configuration and define an incident procedure for wallet compromise, RPC outage and ledger reconciliation failures.
